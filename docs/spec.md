# ループBGM制作ツール 仕様書

<!-- last-reviewed: 2026-11-09 -->

2026-11-09 時点。原本: https://claude.ai/artifact/WGt1Y2SALB1a4Nsmxs64w4

## 1. 概要

AIにテキストの「設計図」を書かせ、プログラムがCC0音源で鳴らして、継ぎ目のないループBGMを書き出すツールを作る。音楽の知識がない人でも、Claude Codeとの会話だけで曲を作り、部分的に直せることを目標にする。

**背景：生成AI（Suno、Stable Audio など）の課題**

- 1〜3分で曲が終わり、ループしない
- 「少し明るく」「少し速く」のように好みへ寄せられず、出直し（ガチャ）を繰り返すしかない
- 「ベースだけ」のような部分的な修正ができない
- 生成物のライセンスが曖昧

**基本方針**

1. AIは曲そのものではなく\*\*設計図（song.json）\*\*を書く。同じ設計図からは毎回同じ曲ができ、Gitで管理できる。
2. 人が作曲する手順どおりに組み立てる：テンポと調 → リズム → ベース → コード → メロディ → アレンジ → ミックス。
3. 音はCC0の単音サンプルと合成音で鳴らす。曲の権利は利用者のものになり、クレジット表記もいらない。
4. パートごとに音声（ステム）を作って保存し、直したパートだけ作り直す。
5. 書き出すたびにプログラムで自動チェックし、問題があればAIが自分で直す。

**対象ユーザー**：音楽の知識がない動画制作者やゲーム制作者で、Claude Code を使える人。

**参考にしたもの**：「しゃりなのループBGM制作キット」（クロノIT）の公開されている機能と考え方。コードは参照せず独自に実装する。YaO、Strudel 系のツール、M6(GPT)3 などの考え方も取り入れる（10章）。

## 2. 全体構成

すべての修正は設計図（song.json）を経由する。AIも試聴UIも音声ファイルを直接加工せず、設計図を変えて書き出し直す。

```text
利用者 ──チャットで頼む──▶ Claude Code（SKILL.md に沿って作曲・修正）
利用者 ──聴く・選ぶ────▶ 試聴UI（再生・比較・修正の選択）
試聴UI ──AIへの依頼（requests/）──▶ Claude Code
試聴UI ──値を直接変える──▶ 設計図 song.json ◀──書く・直す── Claude Code
設計図 song.json ──読む──▶ 書き出しエンジン（bgm render）
    音符に展開 ▶ ステム作成（← 音源：CC0サンプル・合成音）▶ ループ・ミックス ▶ 書き出し（WAV・OGG・MP3）
書き出し ──▶ 自動チェック（report.json）──エラーなら自分で直す──▶ Claude Code
書き出しエンジン ──音を再生──▶ 試聴UI
```

AIへの指示はチャットか試聴UIから入り、設計図を経て書き出しエンジンへ渡る。自動チェックでエラーが出たら、AIが設計図を直してもう一度書き出す。

## 3. 設計図（song.json）の仕様

設計図は、曲ごとに `songs/<曲ID>/song.json` として保存するテキストファイルである。音は**調の中の度数**で、和音はコードの役割（ローマ数字）で書く。このため `key` を1か所変えるだけで、曲全体の調を変えられる（長調から短調への切り替えも含む）。伴奏は「型」を選ぶだけでプログラムが音を作り、AIが音を1つずつ書くのはメロディなど個性が必要な部分だけにする。

### 3.1 記述例

```json
{
  "title": "コインの噴水",
  "usage": "video",
  "style": "comical",
  "tempo": 150,
  "key": "C major",
  "meter": "4/4",
  "form": ["A", "A'", "B", "A"],
  "sections": {
    "A": { "bars": 8, "chords": "I | vi | IV | V | I | vi | ii V | I" },
    "B": { "bars": 8, "chords": "IV | V | iii | vi | IV | V | I | V7" }
  },
  "parts": [
    { "name": "drums",  "role": "rhythm", "kit": ["bongo", "tambourine"], "groove": "bongo_8beat" },
    { "name": "bass",   "role": "bass",   "instrument": "contrabass_pizz", "style": "root_fifth" },
    { "name": "chords", "role": "chords", "instrument": "violin_pizz", "style": "offbeat" },
    { "name": "melody", "role": "melody", "instrument": "xylophone", "grid": "1/8",
      "phrases": { "A": "1 - 3 5 | 6 - 5 . | 4 4 3 2 | 3 - - . | ..." } },
    { "name": "melody_hi", "role": "arrange", "copy": "melody", "octave": 1, "volume": -9 },
    { "name": "sparkle",  "role": "arrange", "instrument": "glockenspiel", "accent": "phrase_start" }
  ],
  "variation": [
    { "section": "A'", "part": "melody", "do": "octave_up" },
    { "every": 8, "part": "drums", "do": "fill_last_bar" }
  ],
  "mix": { "profile": "video", "reverb": "room" }
}
```

### 3.2 曲全体の項目

| 項目 | 内容 | 例 |
| --- | --- | --- |
| `title` | 曲名 | コインの噴水 |
| `usage` | 用途。ミックスと書き出しの初期設定を決める（5.4）。**必須**で、省略すると書き出せない | `video` / `game` / `trpg` |
| `scene` | 使う場面の自由記述。音には影響しない | カフェや日常の場面 |
| `style` | 曲の型（3.8）。楽器と伴奏の型の初期値を決める | `comical` |
| `tempo` | テンポ（1分間の拍数） | 60〜200 |
| `key` | 調。主音＋長調か短調 | `C major`、`A minor` |
| `meter` | 拍子 | `4/4`、`3/4`、`6/8` |
| `swing` | シャッフルの強さ（0〜1） | 0.6 |
| `form` | セクションを並べる順番。最後は最初に戻ってループする | `["A","A'","B","A"]` |
| `sections` | セクションごとの小節数とコード進行 | — |
| `parts` | パートの一覧（3.5） | — |
| `variation` | 周回ごとの変化（3.7） | — |
| `mix` | ミックスの設定（5章） | — |
| `sound` | 鳴らし方。`chip` にするとチップチューン風（9章） | `normal` / `chip` |

`A'` のように `'` を付けた名前は「同じセクションの変形」を表す。コードとメロディは `A` と同じものを使い、`variation` の指定だけが変わる。

### 3.3 調と度数の書き方

- 度数は調の音階の何番目の音かを表す：`1`〜`7`。ハ長調なら `1`=ド、`3`=ミ、`5`=ソ。
- 音階の外の音は `#4`、`b7` のように書く。
- オクターブは `5,`（1つ下）と `1'`（1つ上）で表す。基準の高さは楽器ごとに決めてある。
- 長調と短調を切り替えると、同じ度数がその調の音階で鳴る（ハ長調の `3`=ミは、ハ短調ではミ♭になる）。これで動画の実演と同じ「同じメロディが切なくなる」変化が得られる。
- 例外として、絶対音名でも書ける（`C4:1 E4:1` など。いまの試作の書き方）。絶対音名で書いたパートは、調を変えても音が変わらない。

### 3.4 コード進行の書き方

- 1小節を `|` で区切る。1小節に2つ書くと半分ずつになる（`ii V`）。
- 長調の役割：`I ii iii IV V vi vii°`。短調の役割：`i ii° III iv v VI VII`。
- 付け足し：`7`、`maj7`、`sus4`、`add9`、転回形 `/3`、他の調からの借用 `bVII`、`iv`（長調中）。
- 長調と短調を切り替えたときは、各役割をその調の対応する和音に置き換える（例：`I → i`、`IV → iv`、`V` はそのまま）。
- プログラムは、よく使われるコード進行の型を名前で提供する（例：`pop_axis` = `I | V | vi | IV`、`royal_road` = `IV | V | iii | vi`）。AIはこの型を選んでもよい。

### 3.5 パートの書き方

各パートは `role`（役割）を持ち、作曲の手順と対応する。

| role | 作曲の手順 | 音の作り方 |
| --- | --- | --- |
| `rhythm` | リズム | リズムの型（`groove`）を選ぶか、打楕の並びを書く |
| `bass` | ベース | 伴奏の型（`style`）を選ぶ。コード進行から自動で作る |
| `chords` | コード | 伴奏の型を選ぶ。和音の重ね方（ボイシング）は自動 |
| `melody` | メロディ | AIが度数で書く（鼻歌から取り込むこともできる） |
| `arrange` | アレンジ | 他パートのコピー（オクターブ重ねなど）、飾りの型、対旋律 |

全パート共通の項目：`instrument`（楽器）、`volume`（dB）、`pan`（-1〜1）、`octave`、`mute`、`sections`（鳴らすセクションを限定）。

**メロディの記法**（Strudel の短い記法を参考にした）

- `grid` で　1トークンの長さを決める（例：`1/8` = 8分音符）。
- 度数 = 音を鳴らす。`-` = 前の音を伸ばす。`.` = 休む。`|` = 小節の区切り（拍数が合わなければエラー）。
- 強さは `5>`（強く）、`5<`（弱く）。和音は `[1 3 5]`。
- フレーズはセクションごとに書く（`phrases.A`、`phrases.B`）。

**リズムの記法**：1文字 = 16分音符。`x` = 鳴らす、`X` = 強く、`.` = 休む。

```json
"hits": { "kick": "x...x...x...x...", "snare": "....x.......x...", "hihat": "x.x.x.x.x.x.x.x." }
```

### 3.6 伴奏の型（プログラムが音を作る部分）

M6(GPT)3 の考え方に従い、定番の伴奏は「型の名前」を選ぶだけにする。型はコード進行とテンポから実際の音を作り、楽器の音域を外れたら自動でオクターブを直す。

| 対象 | 型の例（初版で用意するもの） |
| --- | --- |
| ベース | `root_whole`（全音符で根音）、`root_quarter`、`root_fifth`（根音と5度を交互）、`octave_8th`、`walking`（ジャズ）、`arpeggio` |
| コード | `pad`（伸ばす）、`block`（拍ごと）、`offbeat`（裏拍）、`arpeggio_up`、`broken`（分散和音）、`strum`（ギターのようにかき鳴らす）、`waltz` |
| リズム | `8beat`、`16beat`、`shuffle`、`bossa`、`march`、`waltz`、`swing_ride`、`bongo_8beat`、`ambient_none` |
| アレンジ | `phrase_start`（句の頭で飾りの音）、`offbeat_tick`（裏拍に小さな打楽器）、`counter`（メロディの休みに合いの手） |

型はプログラムに追加して増やせる。型で表せないときは、どのパートも音を直接書くことができる。

### 3.7 周回ごとの変化（単調さの対策）

書き出したファイル自体は同じ内容で繰り返す。そこで、**1つのループの中に変化を入れて、繰り返しに気づきにくくする**。

- **セクションの変形**：`A'` でメロディを1オクターブ上げる、楽器を変える、パートを減らす。
- **節目のフィル**：8小節ごとにドラムを変化させる。
- **長さの違うパターンを重ねる**：例えば3拍周期のアルペジオを4拍の上に重ね、重なり方を少しずつずらす。
- **細部のゆらぎ**：強さとタイミングをわずかに変える。乱数のシードを固定するので、同じ設計図からは必ず同じ音が出る。

初期値は曲の型ごとに用意し、AIは必要なときだけ `variation` を書き換える。

### 3.8 曲の型（テンプレート）

曲の型は、楽器編成、伴奏の型、テンポの範囲、周回の変化の初期値をまとめたものである。`templates/<名前>.json` に置き、新しい曲は型を元に作る。初版では次の8種類を用意する。

| 型 | 概要 | 主な楽器 | テンポ | 想定する場面 |
| --- | --- | --- | --- | --- |
| `acoustic` | アコースティック小編成 | ギター、ピアノ、フルート | 80–110 | 日常、解説動画 |
| `pop_groove` | ビートのある明るい曲 | ドラム、ベース、エレキギター、鍵盤 | 100–130 | オープニング、作業 |
| `comical` | コミカル | 木琴、ピチカート、ボンゴ、ファゴット | 120–160 | ギャグ、ハプニング |
| `swing_jazz` | スウィングジャズ | ウッドベース、ピアノ、サックス | 110–180 | 酒場、おしゃれな場面 |
| `drama_strings` | ドラマチックな弦 | 弦楽器、ホルン、ティンパニ | 70–140 | 戦闘、緊張、感動 |
| `ambient` | アンビエント（打楽器なし・長い音） | パッド、ハープ、チャイム | 60–90 | 探索、夜、TRPGの環境音 |
| `folk_town` | 素朴な民族音楽風 | リコーダー、ハープ、タンバリン | 90–130 | 町、村、酒場 |
| `retro_rag` | レトロなラグタイム風 | 古いピアノ、クラリネット | 90–120 | 話し合い、回想 |

ゲームやTRPGでよく使う場面（戦闘、町、ダンジョン、悲しみなど）は、「型＋調＋テンポ」の組み合わせとしてSKILL.mdに対応表を書く（7章）。

### 3.9 設計図の履歴

- 曲ごとに `songs/<曲ID>/history/` へ、変更前の song.json を番号付きで保存する。試聴UIで以前の版と聴き比べて、戻せる。
- リポジトリはGitで管理する。ただし音声ファイルとサンプルは `.gitignore` で除外する。

## 4. 音源

楽器の音は、CC0の単音サンプル（VSCO 2 CE と VCSL）と、プログラムで合成する音の2種類を使う。サンプルはリポジトリに含めず、初回に配布元から取得して照合する。

### 4.1 音源の種類

| 音源 | ライセンス | 主な楽器 | 取得元 |
| --- | --- | --- | --- |
| [VSCO 2 CE](https://github.com/sgossner/VSCO-2-CE) | CC0 | 弦楽器（持続音・ピチカート）、管楽器、ピアノ、マレット（木琴、グロッケンなど）、ハープ、打楽器 | GitHub（コミットを固定） |
| [VCSL](https://github.com/sgossner/VCSL) | CC0 | 民族楽器、ギター類、カリンバ、オカリナ、ハーモニカ、多数の打楽器 | GitHub（コミットを固定） |
| 合成音 | 自作のため制約なし | チップチューン音源、シンセパッド、電子ドラム、弦を弾く音（Karplus-Strong 法） | プログラムに内蔵 |

Sonatina Symphonic Orchestra などCC0でない音源は使わない。これで作った曲は、動画、ゲームへの同梱、販売を含めて自由に使える。

### 4.2 楽器カタログ

`bgm/instruments.py` に楽器の一覧を持ち、楽器ごとに次の情報を決める。

| 項目 | 内容 |
| --- | --- |
| 名前 | 設計図で使う英語名（`xylophone`）と日本語名（木琴）。日本語で頼まれてもAIが対応づけられるようにする |
| 分類 | 鍵盤、マレット、弦、管、打楽器、合成音 |
| 音域 | 鳴らせる最低音と最高音。外れた音は自動でオクターブを直し、チェックで警告する |
| 向いている役割 | メロディ向き、ベース向きなど。AIが楽器を選ぶときの目安にする |
| 音の持続 | 伸ばせる音（弦の持続音）か、すぐ減衰する音（ピチカート、木琴）か |
| 強弱の段階 | サンプルにある強弱の段階と、ラウンドロビン（同じ音の別テイク）の有無 |
| 音量の補正 | 楽器ごとの音量差を揃える値。初回取得時に測って `data/calibration.json` に保存する |

`bgm instruments` コマンドで、楽器の一覧と音域を表示する。試聴UIには、楽器ごとの試し弾きを置く。

### 4.3 取得と照合

1. `data/*-lock.json` に、使うファイルの一覧、ハッシュ値（Gitのblob SHA-1）、サイズ、取得元のコミットを固定しておく（試作で実装済み）。
2. `bgm fetch` で必要なファイルだけを並列で取得し、ハッシュ値を照合する。一致しないファイルは捨てて取り直す。
3. 楽器を指定して一部だけ取得できる（`bgm fetch xylophone`）。チップチューン風だけ使うなら取得は不要。
4. 取得量の目安は数百MB〜1GB程度。実際の量は楽器を選んだ後に確定する。

### 4.4 サンプラーの動作

- 鳴らしたい音にいちばん近い高さのサンプルを選び、再生速度を変えて音程を合わせる。
- 強さに応じて強弱の段階を選び、同じ音が続くときはラウンドロビンで別テイクを使う（機械的な響きを避けるため）。
- 音の長さに合わせて余韻を残して消す（リリース）。伸ばせない楽器は自然に減衰させる。

## 5. 書き出し処理

設計図からパートごとの音声（ステム）を作り、ミックスして、継ぎ目のないループとして書き出す。変更がないパートは前回のステムをそのまま使うので、一部を直したときの作り直しは数秒で終わる。

### 5.1 処理の順番

1. **読み込みと検査**：song.json を読み、書式の誤り（小節の拍数の不一致、存在しない楽器名など）を、場所を示した日本語のエラーで返す。
2. **音符への展開**：度数、コード、伴奏の型、周回の変化を、「いつ・どの高さを・どの強さで」という音符の列に変換する。この結果は `build/notes.json` に保存し、チェック（6章）で使う。
3. **ステムの作成**：パートごとに音符を鳴らして音声にする。
4. **ループ処理**：曲の終わりからはみ出した音を、曲の頭に重ねる（5.3）。
5. **ミックス**：音量、定位、音質の調整、残響をかけてまとめる（5.4）。
6. **仕上げ**：全体の音量を目標の大きさに揃え、音割れを防ぐ。
7. **書き出しとチェック**：各形式で保存し、自動チェックを実行する。

### 5.2 パートごとのキャッシュ

- 各パートについて、パートの設定と、音に影響する曲全体の設定（テンポ、調、コード進行、形式）からハッシュ値を作る。
- ハッシュ値が前回と同じパートは、保存済みのステムを使う。
- 音量と定位はミックスの段階でかけるので、変えてもステムは作り直さない。
- 試作で実装済み（`render.py` の `part_hash`）。エンジンの版が変わったら全パートを作り直す。

### 5.3 ループ処理

継ぎ目をなくすため、曲を「輪」として扱う（LoopGen と同じ考え方）。

- ループの長さは、小節数とテンポから決まる正確なサンプル数にする。
- 曲の最後で鳴った音の余韻や残響は、切り捨てずに曲の頭へ重ねる。これで、ループして最初に戻った瞬間も、前の周の響きが自然に続く。
- 残響は曲の末尾だけでなく周回の継ぎ目も含めて計算する（曲を2周分鳴らして、2周目を切り出すのと同じ結果になる）。
- 試作で実装済み（`fold_loop`）。

### 5.4 ミックス

| 処理 | 内容 |
| --- | --- |
| 音量と定位 | パートごとの `volume`（dB）と `pan`。省略時は役割ごとの初期値（ベースとメロディは中央、伴奏は左右に少し散らす） |
| 低音の整理 | ベースとキック以外のパートの不要な低音を削り、音がこもるのを防ぐ |
| 声の帯域を空ける | 動画やTRPGで声と重なるときに使う。声の聞き取りやすさに影響する帯域（およそ1〜4kHz）を、伴奏パートで少し下げる |
| 残響 | `room` / `hall` / `plate` / `none`。パートごとにかける量を変えられる |
| 音量を揃える | 全体の音量を目標のラウドネス（LUFS）に合わせ、最大値を -1dB 以下に抑える |

用途（`usage`）ごとに、次の初期設定（プロファイル）を用意する。値は初版の仮の値で、実際に聴いて調整する。

| プロファイル | 目標の音量 | 声の帯域 | ループの長さの目安 | 標準の出力 |
| --- | --- | --- | --- | --- |
| `video`（動画） | -16 LUFS | 空ける | 60–120秒 | WAV、MP3、長尺版 |
| `game`（ゲーム） | -16 LUFS | 空けない | 60–180秒 | OGG（ループ情報付き）、WAV |
| `trpg`（TRPGのセッション） | -20 LUFS | 空ける | 120–300秒 | OGG、MP3、長尺版 |

TRPG用は、会話の邪魔にならないように音量を低めにし、変化を穏やかにして、長い時間流しても疲れないようにする。

### 5.5 出力形式

| 出力 | 形式 | 用途と注意点 |
| --- | --- | --- |
| マスター | WAV（44.1kHz、16bit、ステレオ） | どの用途でも作る。継ぎ目が完全に一致する |
| ゲーム用 | OGG Vorbis ＋ `LOOPSTART` / `LOOPLENGTH` タグ | RPGツクールなどがこのタグでループする。Unity と Godot ではエンジン側のループ設定を使う |
| 配布用 | MP3（192kbps） | MP3は先頭に無音が入るため、プレイヤーによっては継ぎ目が少し途切れる。その旨を書き出し時に表示する |
| 長尺版 | WAV / MP3 | 指定した長さ（例：10分、30分）までループを繰り返し、最後はフェードアウトする。継ぎ目の問題が起きないので、動画編集やTRPGツールで使いやすい |
| ステム | WAV（パートごと） | 別のソフトでミックスし直したい人向け |

書き出し先は `songs/<曲ID>/out/` とする。WAV、OGG、MP3 の書き出しは soundfile（libsndfile）で行い、OGGのタグは mutagen で書き込む。ffmpeg は必須にしない。

### 5.6 部分的な書き出し

AIとのやり取りを速くするため、次の試聴用の書き出しを用意する。

- `--parts bass,melody`：指定したパートだけで書き出す（作曲の各段階で聴くため）。
- `--bars 1-8`：指定した小節だけ書き出す。
- `--seam`：継ぎ目の前後各数秒だけをつなげて書き出し、継ぎ目を耳で確かめられるようにする。

## 6. 自動チェックと修正ループ

書き出すたびにプログラムが曲を検査し、結果を `songs/<曲ID>/out/report.json` に保存する。AIはこの結果を読み、問題があれば利用者に聴かせる前に自分で直す（YaO の考え方）。音楽の知識がなくても、明らかにおかしい曲を聴かされる回数を減らすのが目的である。

### 6.1 チェック項目

各項目は「エラー（必ず直す）」か「警告（曲の意図によってはそのままでよい）」のどちらかに分ける。判定のしきい値は初版の仮の値で、実際に聴いて調整する。

| 分類 | 項目 | 判定の例 | 重さ |
| --- | --- | --- | --- |
| ループ | 継ぎ目のプツッという音 | 継ぎ目で波形が飛んでいる、または音の変化量が他の場所より極端に大きい | エラー |
| ループ | 継ぎ目での音量の段差 | 終わりの数秒と頭の数秒の音量差が 3dB 以上 | 警告 |
| ループ | 長さ | 用途ごとの目安（5.4）から外れている | 警告 |
| 音量 | 音割れ | 最大値が -1dB を超える | エラー |
| 音量 | 目標の音量 | 目標の LUFS から ±1 LU 以上ずれている | エラー |
| 音量 | パートのバランス | メロディが伴奏に埋もれている、または1つのパートだけが極端に大きい | 警告 |
| 音程 | 楽器の音域外 | サンプルで鳴らせない高さの音がある | エラー |
| 音程 | コードに合わない音 | 強拍でコードに含まれないメロディの音が 30% を超える | 警告 |
| 音程 | メロディの音域 | 最低音と最高音の幅が1.5オクターブを超える、または1オクターブ以上の跳躍が多い | 警告 |
| 音程 | パート同士のぶつかり | メロディと伴奏が同じ高さで長く重なる、ベースより低い伴奏がある | 警告 |
| 単調さ | 同じ小節の繰り返し | 全パートがまったく同じ小節の割合が 50% を超える | 警告 |
| 用途 | 声とのぶつかり | 動画とTRPGのとき、声の帯域の音が多すぎる | 警告 |

音程の項目は、音声ではなく音符の列（`build/notes.json`）を検査するので、正確で速い。

### 6.2 修正ループ

1. AIが設計図を書くか直して、書き出す。
2. チェックでエラーがあれば、AIが自分で直して書き出し直す。自動で直すのは最大3回までとする。
3. 3回で直らなければ、利用者に状況を説明して方針を聞く。
4. 警告は自動では直さない。曲を聴かせるときに「メロディが少し埋もれ気味です」のように、分かりやすい言葉で一緒に伝える。

### 6.3 報告の形式

```json
{
  "song": "coin_fountain", "version": 7, "passed": false,
  "metrics": { "lufs": -15.8, "peak_db": -1.4, "loop_seconds": 51.2 },
  "issues": [
    { "level": "error", "check": "range", "part": "melody", "bars": [5],
      "message": "木琴で鳴らせない高さの音があります（C8）", "hint": "octave: -1" }
  ]
}
```

各問題には、パート名、小節番号、日本語の説明、直し方のヒントを付ける。AIはこのヒントを手がかりに直す。

## 7. AIとの作業手順

利用者はClaude Codeに日本語で頼むだけでよい。作曲の手順、曖昧な指示の読み替え方、コマンドの使い方は、すべてAI向けの手順書に書いておく。

### 7.1 手順書のファイル

| ファイル | 内容 |
| --- | --- |
| `CLAUDE.md` | リポジトリの概要、初回の準備の進め方、禁止事項（サンプルを直接編集しない、ステムを手で加工しないなど） |
| `.claude/skills/loop-bgm/SKILL.md` | 作曲と修正の手順。下の 7.3〜7.5 の内容 |
| `docs/song-format.md` | 設計図の全項目の説明（3章の詳細版） |
| `docs/patterns.md` | 伴奏の型、コード進行の型、曲の型の一覧と音の特徴 |

### 7.2 コマンド

| コマンド | 動作 |
| --- | --- |
| `bgm doctor` | 環境を診断する（Python、ライブラリ、音源の取得状況） |
| `bgm fetch [楽器...]` | 音源を取得して照合する |
| `bgm instruments` | 楽器の一覧と音域を表示する |
| `bgm new <曲ID> --style <型>` | 曲の型から設計図の雛形を作る |
| `bgm render <曲ID> [--parts] [--bars] [--seam]` | 書き出して、チェックを実行する |
| `bgm check <曲ID>` | チェックだけ実行する |
| `bgm export <曲ID> [--long 10m] [--stems]` | 配布用の形式で書き出す |
| `bgm se <曲ID> --bars 13-16` | 効果音を切り出す（9章） |
| `bgm hum <録音.wav> <曲ID>` | 鼻歌をメロディにする（9章） |
| `bgm serve` | 試聴UIを起動する（8章） |

### 7.3 初回の準備

利用者が「BGMを作りたい」と頼むと、AIは次の順に進める。

1. `bgm doctor` で環境を確認し、足りないものを案内する。
2. `bgm fetch` で音源を取得する（容量と所要時間を先に伝える）。
3. 見本の曲を1曲書き出し、試聴UIを開いて聴いてもらう。

### 7.4 作曲の手順

人が作曲する順番どおりに組み立てる。利用者は次の2つの進め方を選べる。

- **おまかせ**：1〜7を一気に進め、完成した曲だけを聴いてもらう。初期値はこちら。
- **1段階ずつ**：各段階で `--parts` を使って書き出し、聴いてもらってから次へ進む。

1. **意図を聞く**：用途、場面、雰囲気、長さを聞く。分からなければ、曲の型と場面の対応表（7.6）から候補を出す。
2. **テンポと調、曲の型**を決め、`bgm new` で雛形を作る。
3. **構成とコード進行**を決める（`form` と `sections`）。
4. **リズム**を置く。
5. **ベースとコード**の伴奏の型を選ぶ。
6. **メロディ**を書く。コードの音を強拍に置き、句の終わりを安定した音（1、3、5度）にする。
7. **アレンジと周回の変化**を足し、ミックスのプロファイルを確認する。
8. **書き出しとチェック**をし、エラーがあれば自分で直す（6章）。
9. **聴いてもらう**：曲の説明と1〜3件の改善案を、音楽用語を使わずに伝える。

### 7.5 曖昧な指示の読み替え

利用者は音楽の言葉を知らない前提で、よくある指示を設計図の変更に読み替える対応表をSKILL.mdに持つ。初版では次のような内容にする。

| 指示 | 設計図の変更（例） |
| --- | --- |
| もっと明るく | 長調にする、テンポ +10、メロディを高く、音色の明るい楽器（グロッケン、木琴） |
| 切なく / 暗く | 短調にする、テンポ -10、弦の持続音を使う |
| 落ち着いた感じに | テンポを下げる、伴奏を `pad` にする、打楽器を減らす |
| 盛り上げて | ドラムを `16beat` にする、ベースを `octave_8th` にする、メロディを重ねる |
| もっと控えめに（BGMとして） | メロディの音量を下げる、音数を減らす、声の帯域を空ける |
| うるさい / ごちゃごちゃしている | パートを減らす、伴奏の型を単純にする |
| 寂しい / 物足りない | アレンジのパートを足す、周回の変化を増やす |
| 飽きる | ループを長くする、Bセクションを足す、周回の変化を増やす |

対応表にない指示も、AIが解釈して設計図を変える。ただし大きく変えるときは、変更内容を先に1行で伝える。

### 7.6 場面と曲の型の対応表

ゲームとTRPGでよく使う場面を、曲の型、調、テンポの組み合わせで示す。

| 場面 | 曲の型 | 調 | テンポ |
| --- | --- | --- | --- |
| 町・村 | `folk_town` | 長調 | 100–120 |
| フィールド・冒険 | `drama_strings` / `pop_groove` | 長調 | 110–140 |
| ダンジョン・探索 | `ambient` | 短調 | 60–90 |
| 戦闘 | `drama_strings` | 短調 | 140–170 |
| 緊張・謎解き | `ambient` / `drama_strings` | 短調 | 70–100 |
| 悲しみ・回想 | `acoustic` / `retro_rag` | 短調 | 60–80 |
| 日常・解説 | `acoustic` | 長調 | 80–110 |
| ギャグ・ハプニング | `comical` | 長調 | 130–160 |
| 酒場 | `swing_jazz` / `folk_town` | 長調 | 110–140 |

### 7.7 試聴UIからの修正依頼の処理

試聴UIで利用者が選んだ修正のうち、AIが必要なものは `songs/<曲ID>/requests/` に依頼ファイルとして保存される（8章）。利用者がClaude Codeで「UIの依頼を処理して」と頼むと、AIは未処理の依頼を古い順に読み、設計図を直して書き出し、依頼を処理済みにする。

## 8. 試聴UI

`bgm serve` で手元のブラウザに開く画面（`http://localhost:8765`）で、曲を聴き、比べ、書き出し、修正を頼める。修正には2種類ある。値を変えるだけの修正はUIがその場で行い、考える必要がある修正はAIに頼む。

### 8.1 画面と機能

| 画面 | 機能 |
| --- | --- |
| 曲の一覧 | 曲名、型、テンポ、長さ、更新日時、チェックの結果。曲名で絞り込む |
| 再生 | 継ぎ目のないループ再生、波形と小節番号の表示、任意の小節から再生、「継ぎ目を聴く」ボタン（終わりの5秒前から再生） |
| パート | パートごとのミュートとソロ、音量。ステムをブラウザ内で重ねて鳴らすので、書き出し直さずにすぐ反映される |
| 履歴 | 設計図の版の一覧。版ごとの変更内容の要約、2つの版を切り替えて聴き比べる機能（A/B）、前の版に戻す機能 |
| チェック | 自動チェックの結果を日本語で表示する。問題のある小節を波形上に印で示す |
| 書き出し | 形式（WAV / OGG / MP3 / 長尺版 / ステム）を選んで書き出す。長尺版は長さを選ぶ |
| 効果音 | 波形上で小節を選んで切り出す（9章） |
| 鼻歌 | マイクで録音するか、音声ファイルを選んで取り込む（9章） |
| 楽器 | 楽器ごとの試し弾き（音階を鳴らす） |

### 8.2 その場でできる修正（AI不要）

設計図の値を直接変えて書き出し直す。変更したパートだけが作り直されるので、数秒で結果を聴ける。

| 操作 | 変更する項目 |
| --- | --- |
| テンポ（±5、±10、数値入力） | `tempo` |
| 長調・短調の切り替え、音の高さを上げ下げ | `key` |
| パートの楽器の差し替え（その役割に向く楽器から選ぶ） | `parts[].instrument` |
| パートの音量を確定する、パートを外す | `parts[].volume`、`parts[].mute` |
| 伴奏の型の差し替え | `parts[].style`、`parts[].groove` |
| 残響、用途のプロファイル | `mix` |
| 鳴らし方の切り替え（通常 / チップチューン風） | `sound` |

### 8.3 AIに頼む修正

- 対応表（7.5）の指示をボタンとして並べる（「もっと明るく」「控えめに」「飽きる」など）。
- 対象のパートや小節を選んでから頼める（例：ベースを選んで「音数を減らす」）。
- 自由に文章も入力できる。
- 依頼は `songs/<曲ID>/requests/<日時>.json` に保存し、UIに「未処理」と表示する。
- 利用者がClaude Codeで「UIの依頼を処理して」と頼むと、AIが処理する（7.7）。書き出しが終わると、UIが自動で新しい版を読み込む。

### 8.4 実装の方針

- サーバーはPythonの標準ライブラリだけで作る。自分のPCからだけ接続できるように、`127.0.0.1` で待ち受ける。
- 画面はHTMLとJavaScriptの1ページで作り、ビルドの手順を必要としない。
- 再生には Web Audio API を使い、継ぎ目なくループさせる（`<audio>` 要素のループは継ぎ目で途切れることがあるため使わない）。
- ファイルの更新を数秒おきに確かめ、AIやコマンドが書き出した新しい版を反映する。

## 9. 追加機能

効果音の切り出し、チップチューン風、鼻歌からのメロディの3つを作る。どれも同じ設計図と書き出しの仕組みの上に作り、別のツールにはしない。MIDIの書き出しは対象外とする（必要になれば、音符の列から後で追加できる）。

### 9.1 効果音の切り出し

曲の一部から、場面転換などに使う短い音を作る。曲と同じ楽器と調なので、BGMと一緒に流しても統一感が出る。

| 種類 | 長さの目安 | 作り方 |
| --- | --- | --- |
| ジングル | 3–8秒 | 指定した小節を切り出し、最後に主和音（I）を鳴らして終わらせる。余韻を残して自然に消す |
| スティンガー | 1–3秒 | 曲の楽器で和音を1回鳴らす。飾りの音（グロッケンなど）を重ねる |
| アイキャッチ | 2–5秒 | メロディの頭のフレーズだけを、伴奏を薄くして鳴らす |

- 試聴UIで小節を選ぶか、`bgm se <曲ID> --bars 13-16 --kind jingle` で作る。AIに「この曲から場面転換の音を作って」と頼むこともできる。
- 出力はループしないWAVとOGG。音量は曲と同じプロファイルに合わせる。
- 設計図に `se` の項目として残し、曲を直したときに一緒に作り直せるようにする。

### 9.2 チップチューン風

設計図の `sound` を `chip` にすると、同じ曲を古いゲーム機のような電子音で鳴らす。音源の取得は不要。

| チャンネル | 音 | 担当する役割 |
| --- | --- | --- |
| 矩形波1 | 四角い波（音色を変える幅：12.5% / 25% / 50%） | メロディ |
| 矩形波2 | 同上 | コード（速い分散和音にして1音ずつ鳴らす）、またはハモリ |
| 三角波 | やわらかい低い音 | ベース |
| ノイズ | 雑音 | 打楽器（キック、スネア、ハイハットを雑音の長さと高さで作り分ける） |

- 同時に鳴らせるのは各チャンネル1音、合計4音までという制約を守る。役割からチャンネルを自動で割り当て、入りきらないアレンジのパートは省く。
- 割り当ては設計図の `chip` 項目で上書きできる（例：矩形波2にアレンジの対旋律を入れる）。
- 音の揺らぎ（ビブラート）、音量の変化、ごく短いエコーで、当時らしい表現を加える。残響は初期値ではかけない。
- 特定のゲーム機の音を忠実に再現することは目指さず、「それらしい」音を独自に合成する。

### 9.3 鼻歌からメロディ

録音した鼻歌の音程を取り出し、設計図のメロディ（度数の記法）にする。

1. **録音**：試聴UIでマイクから録音する（音声ファイルの指定も可）。録音中は曲のテンポでクリック音（メトロノーム）を鳴らし、伴奏も一緒に流せるようにする。拍に合わせて歌えるので、次の拍への合わせ込みが正確になる。
2. **音程の推定**：pYIN 法で、短い時間ごとに音の高さを推定する。
3. **音符に分ける**：高さが安定している区間を音符とし、声の出だしで区切る。
4. **拍と調に合わせる**：音符の長さを曲の拍（`grid`）に、音の高さを曲の調の音階に合わせ、度数に変換する。曲がまだないときは、鼻歌から調とテンポを推定する。
5. **設計図に入れる**：結果をメロディのフレーズとして保存し、自信の低い音に印を付ける。AIがその部分を整え、元の鼻歌と並べて聴けるようにする。

音程の推定には librosa を使う。依存ライブラリが大きいため、鼻歌機能を使うときだけ追加で導入する（`pip install -e .[hum]`）。鼻歌の音声そのものは曲に入れない。

## 11. 開発の進め方（DXForgeEX のハーネスを流用）

AIへの指示書、フック、Codexによるレビュー、自動マージ、Orcaのワーカー運用は、DXForgeEX（`F:\HAL\Self\DXForgeEX`）の仕組みをそのまま移す。変えるのは、言語がPythonであることに伴う部分と、GUI確認の代わりに試聴確認を置く部分だけである。

### 11.1 リポジトリとブランチ

- GitHub の `nel2116/loop-bgm` を**公開**で作る。
- `main` と `develop` の2本を使う。PRは `develop` に出し、区切りで `main` に上げる。
- `develop` のブランチ保護で、CIの各ジョブ、`No hold label`、`codex-review` を必須にする。人の承認ゲート（DXForgeEX の #160）は仕組みだけ移し、無効にしておく。
- コミットメッセージ、PR、Issue、コードコメントは日本語。コミットの件名は `[add]` / `[fix]` / `[chore]` で始め、`(#N)` で終える。PR本文は「概要」「変更点」「動作確認」「自己点検」と `Closes #N`。
- 公開リポジトリなので、音源（`samples/`）、書き出した音（`songs/*/out/`、`build/`）、録音した鼻歌はコミットしない。`.gitignore` に加え、規約チェックでも音声ファイルの追加を弾く。

### 11.2 AI向けの文書


| 文書 | 内容 |
| --- | --- |
| `AGENTS.md` | AI向けの地図。ビルドを壊す規則、コマンド、完了の定義。短く保ち、規則は同じ失敗が2回起きてから足す |
| `CLAUDE.md` | `@AGENTS.md` と Claude Code 専用の注意、要約時に残す内容 |
| `docs/dev/` | `Architecture.md`、`BuildAndTest.md`、`ReviewAndMerge.md`、`WorkerRules.md` |
| `docs/design/` | 設計判断の記録。1判断1ファイル（例：度数記法、ループ処理、音量の目標値） |
| `docs/ListeningCheck.md` | 人が耳で確かめる手順（DXForgeEX の `ManualVerification.md` にあたる） |
| `README.md` | 人向けの概要（日本語） |

この仕様書の内容は、実装しながら `docs/design/` と `docs/song-format.md` へ移していく。移した後はリポジトリの文書を正とする。

### 11.3 フックとチェック

各フックには DXForgeEX と同じくテストを付け、CIで実行する。

### 11.4 テストとCI

- **単体テスト（pytest）**：度数から音高への変換、長調と短調の切り替え、伴奏の型、設計図の書式エラー、ループの長さがサンプル単位で正しいこと、継ぎ目の連続性、チェックがわざと入れたプツッという音や音域外の音を検出すること、OGGのループ情報のタグ。
- **回帰テスト**：見本曲を合成音だけで書き出し、音符の列（`notes.json`）は完全一致、音の数値（音量、最大値、継ぎ目）は許容幅つきで基準と比べる。音を意図して変えるPRは、理由を書いて同じPRで基準を更新する。
- **サンプルを使うテスト**：CIでは音源を取得しない。サンプラーを変えたときだけ、PrePr が手元で実行する。
- **CI**：GitHub Actions（windows-latest）で ruff、pytest、規約チェック、フックのテスト、PowerShell スクリプトのテストを実行する。公開リポジトリなので実行時間は無料。
- **速い確認用コマンド**：`python -m pytest -q -m "not slow"`（数秒）。

### 11.5 PRの流れ

1. Issue を作る（`create-issue` スキル：現象、原因、対応案、完了条件）。
2. コーディネーターが指示を書き（`orchestration-prompt` スキル）、ワーカーが専用の worktree で実装する。区切りごとにコミットして push する。
3. `./PrePr.ps1` が差分に応じて必要な検査を実行し、スタンプを残す。スタンプがないと `gh pr create` はフックで止まる。
4. CIが通ったら、ワーカーが `./CodexReview.ps1 -Pr <N> -Post` を実行し、指摘を直すか理由を返す。PASSしたら「PR 準備完了」を送る。
5. コーディネーターが `-SetStatus` で自動マージし、`./CleanupMerged.ps1` で片付ける。
6. 音が変わるPRは、本文に「試聴メモ」（どの見本曲のどこがどう変わるか、比較用の書き出しコマンド）を書く。マージは止めない。

### 11.6 試聴確認（節目だけ）

AIは音の良し悪しを判断できないので、ここだけは人が担う。DXForgeEX のGUI確認と違い、PRごとには止めない。

- **見本曲のセット**：曲の型ごとに1曲、チップチューン風、特殊な例（3拍子、シャッフル、短調）を `songs/examples/` に置く。回帰テストもこの曲を使う。
- **節目**：各フェーズの終わりに、AIが見本曲をすべて書き出し、変わった曲は前の版と並べて聴けるようにする。そのフェーズの試聴メモをまとめたチェックシートをIssueにする。
- **結果**：利用者が聴いて気になった点をそのIssueに書き、AIが個別のIssueに分ける。
